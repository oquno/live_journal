# ライブ記録アプリ仕様書

## 1. 目的

ライブを見た記録を、手間なく残して後から見返せる Web アプリケーションを作る。

重視する点:

- 入力が軽いこと
- 演者ごとの「何回目に見たか」を自動で出せること
- 時系列で振り返りやすいこと
- 演者・会場・日付などで検索しやすいこと
- セルフホストしやすく、できれば Cloudflare の無料枠でも運用可能なこと
- 自分で読んで直しやすいこと

## 2. 元メモから整理した要件

`doc/README.md` から読み取れるコア要件は以下。

- エントリーとしてライブ記録を残せる
- エントリーに場所、演者一覧、購入したもの、関連ブログを持てる
- 演者ごとに「今回が何回目か」を自動表示したい
- 演者ページから、その演者を見た記録を時系列で一覧したい
- 外部リンクを持てる
  - ブログ記事
  - Scrapbox 上の購入物ページ
  - Flickr アルバム
  - Last.fm の該当演者ページ

## 3. 想定ユーザー

- 主に自分 1 人で使う
- ログインユーザーも基本 1 人
- 公開範囲は以下のどちらでもよい
  - 非公開の個人日記
  - 一部を公開できる個人記録サイト

この前提により、マルチテナントや複雑な権限管理は不要とする。

## 4. 方式選定

### 4.1 候補

#### A. ファイルベース（Markdown / JSON）

利点:

- バックアップしやすい
- Git 管理しやすい
- 実装が単純に見える

欠点:

- 演者ごとの通算回数計算や検索で実装が煩雑になる
- 一覧・検索・並び替えのたびに集計処理が必要
- 関連データ（演者、会場、購入物）を正規化しづらい
- 将来的な UI の拡張で破綻しやすい

#### B. SQLite

利点:

- 単一ファイルで扱えて軽い
- 集計・検索・並び替えが簡単
- セルフホストしやすい
- バックアップが容易
- 1 人利用なら十分以上に高速

欠点:

- Markdown 直編集ほどの可搬性はない
- 書き込み競合には強くないが、今回の用途では問題になりにくい

#### C. Cloudflare D1

利点:

- Cloudflare 無料枠で完結しやすい
- Workers と相性がよい

欠点:

- ローカルや他環境でのセルフホスト性は SQLite より落ちる
- ローカル開発と本番の差分を多少意識する必要がある

### 4.2 採用

MVP の保存方式は **SQLite** を採用する。

理由:

- 「軽さ」と「検索性」を最も両立しやすい
- セルフホスト前提に自然
- SQLite ベースの実装は、後から Cloudflare D1 に寄せやすい
- ファイルベースより、演者通算回数や絞り込みの実装が素直

### 4.3 デプロイ方針

第一候補:

- アプリ本体: 軽量な Web アプリ
- DB: SQLite
- 配置: VPS / 自宅サーバ / Fly.io 相当 / Docker

第二候補:

- アプリ本体: Cloudflare Workers
- DB: D1

そのため、アプリケーション層では SQL をできるだけ素直に保ち、SQLite と D1 の両方で成立しやすいスキーマを意識する。

## 5. スコープ

### 5.1 MVP に含める

- ライブ記録の作成、編集、削除

- 演者ページでの出演記録一覧
- 会場ページでの開催記録一覧
- フリーワード検索
- 日付範囲、演者、会場による絞り込み

  - ブログ

  - Last.fm
  - 購入物リンク

### 5.2 MVP では後回し

## 6. ユースケース

### 6.1 記録を追加する

1. ユーザーは新規エントリー画面を開く
2. 開催日、会場、演者を入力する
3. 任意で購入物、ブログ URL、Flickr URL、メモを追加する
4. 保存する
5. 保存後、各演者について「今回が何回目か」が表示される

### 6.2 演者の記録を見返す

1. エントリー詳細で演者名をクリックする
2. 演者ページへ移動する
3. 該当演者が出演したエントリーが日時順で表示される
4. 各行で「何回目の観覧だったか」も確認できる

### 6.3 条件で探す

1. 一覧ページでキーワードを入力する
2. 必要に応じて演者、会場、日付範囲を指定する
3. 条件に一致するエントリーを絞り込んで見る

## 7. 画面仕様

### 7.1 一覧画面

目的:

- 最近のライブ記録を時系列で眺める
- 条件検索の起点にする

表示項目:

- 開催日
- イベント名（任意）
- 会場名
- 演者一覧
- メモ冒頭
- 添付リンク有無

操作:

- キーワード検索
- 演者で絞り込み
- 会場で絞り込み
- 日付範囲で絞り込み
- 新規作成

並び順:

- デフォルトは開催日降順

### 7.2 詳細画面

表示項目:

- 開催日
- イベント名
- 会場
- 演者一覧
  - 各演者について「今回が何回目か」を表示
- 購入物一覧
- ブログ URL
- Flickr URL
- Last.fm URL
- メモ本文
- 作成日時
- 更新日時

操作:

- 編集
- 削除
- 演者ページへ遷移
- 会場ページへ遷移

### 7.3 新規作成・編集画面

入力項目:

- 開催日（必須）
- イベント名（任意）
- 会場（必須）
- 演者一覧（1 件以上必須）
- 購入物一覧（任意、複数可）
- ブログ URL（任意）
- Flickr URL（任意）
- メモ（任意）
- 公開フラグ（任意、将来拡張用）

UI 方針:

- 演者と購入物は追加可能なリスト入力
- 既存演者・既存会場はサジェストを出す
- 保存前に複雑な確認ダイアログは出さない

### 7.4 演者ページ

表示項目:

- 演者名
- Last.fm URL
- 観覧回数合計
- 出演記録一覧
  - 開催日
  - 会場
  - 何回目だったか
  - エントリーへのリンク

並び順:

- 開催日昇順を基本
- 切替で降順も可能

### 7.5 会場ページ

表示項目:

- 会場名
- 開催記録一覧
- 開催回数

## 8. データモデル

### 8.1 テーブル一覧

#### entries

ライブ記録本体。

- id
- event_date
- title
- venue_id
- notes
- blog_url
- flickr_url
- visibility
- created_at
- updated_at

#### artists

演者マスタ。

- id
- name
- slug
- lastfm_url
- created_at
- updated_at

#### venues

会場マスタ。

- id
- name
- slug
- created_at
- updated_at

#### entry_artists

エントリーと演者の中間テーブル。

- id
- entry_id
- artist_id
- billing_order

`billing_order` は表示順保持用。

#### purchases

購入物。

- id
- entry_id
- item_name
- item_url
- notes
- display_order

#### auth_users

管理用ユーザー。MVP では 1 ユーザーでもテーブルは持っておく。

- id
- login_id
- password_hash
- created_at
- updated_at

### 8.2 制約

- `entries.event_date` は必須
- `entries.venue_id` は必須
- 1 エントリーに演者は 1 件以上必須
- `artists.name` は一意
- `venues.name` は一意
- URL 項目は http/https のみ許可

### 8.3 インデックス

- `entries(event_date desc)`
- `artists(name)`
- `venues(name)`
- `entry_artists(artist_id, entry_id)`
- `purchases(entry_id, display_order)`

## 9. 通算回数の定義

演者の「何回目か」は、対象エントリーの日付時点までの、その演者を含むエントリー数で決める。

例:

- 2026-01-10 に A を見た
- 2026-02-01 に A を見た

このとき 2026-02-01 のエントリーでは A は 2 回目。

### 9.1 同日複数エントリー

同じ演者を同日に複数回見た場合の順序決定が必要なので、以下の順で並べる。

1. `event_date`
2. `entries.created_at`
3. `entries.id`

これにより、同日データでも通算順が安定する。

### 9.2 表示方法

- 詳細画面で各演者の横に `3回目` のように表示する
- 演者ページ一覧でも各エントリーに表示する

## 11. 認証・公開範囲

### 11.1 MVP の認証

- 管理者 1 ユーザーのログインを用意する
- 記録の作成、編集、削除はログイン必須

### 11.2 公開閲覧

初期案は 2 パターンのどちらでも運用できるようにする。

- 非公開モード

- 公開モード

  - 作成、編集、削除のみログイン必須

MVP 実装時は環境変数で切り替える。

## 12. 非機能要件

### 12.1 性能

- 一覧表示は 500〜3000 件程度の記録で快適に動くこと
- 検索結果は通常 1 秒以内を目標

### 12.2 可用性

- 単一ノード運用前提
- DB バックアップを取りやすいこと

### 12.3 保守性

- 複雑な外部依存を避ける
- できるだけ少ないプロセス数で動く
- DB スキーマ変更はマイグレーションで管理する

## 13. 技術方針

### 13.1 推奨構成

軽量さに加えて、実装者本人が読みやすく保守しやすいことを優先して、以下を推奨する。

- フロントエンド: サーバーサイドレンダリング中心
- バックエンド: 単一プロセスの Web アプリ
- DB: SQLite

具体的な候補:

- 第一候補: `Go + html/template + SQLite`
- 第二候補: `Go + templ + SQLite`
- 第三候補: `TypeScript + Hono + SQLite/D1`

### 13.2 第一候補を推す理由

`Go + html/template + SQLite` は以下の点で強い。

- 単一バイナリにまとめやすい
- セルフホストが非常に楽
- 小規模 CRUD に十分
- 標準ライブラリ中心で依存が少ない
- 自分で読んだときに処理の流れを追いやすい

`templ` は便利だが、まずは新しいテンプレート記法を増やさないほうが保守しやすい。よって初期実装では標準の `html/template` を優先する。

### 13.3 今回の結論

仕様段階では、**データモデルは SQLite を正として設計し、初期実装は `Go + html/template + SQLite` を第一候補**とする。

理由:

- 実装と運用が単純
- 依存が少なく、自分で保守しやすい
- 小さく作ってから別実装へ置き換える土台にしやすい

### 13.4 書き換え前提の設計方針

将来 `Hono + D1` や別構成へ書き換える可能性を考えて、以下を守る。

- 画面の都合で DB スキーマをゆがめない
- ルーティング層、データアクセス層、HTML 描画層を分ける
- ビジネスルールは SQL か専用関数に閉じ込める
- 外部 API 連携は初期実装に入れすぎない

これにより、最初は保守しやすい Go 実装で始め、必要になった時点で別ランタイムへ移植しやすくする。

## 14. API / 画面ルーティング案

### 14.1 画面ルート

- `GET /` 一覧画面
- `GET /entries/new` 新規作成画面
- `GET /entries/:id` 詳細画面
- `GET /entries/:id/edit` 編集画面
- `GET /artists/:slug` 演者ページ
- `GET /venues/:slug` 会場ページ
- `GET /login` ログイン画面

### 14.2 更新系ルート

- `POST /entries`
- `POST /entries/:id`
- `POST /entries/:id/delete`
- `POST /login`
- `POST /logout`

MVP では HTML フォーム POST 中心でよい。SPA 化は不要。

## 15. 一覧取得ロジック

一覧画面では以下を返す。

- エントリー本体
- 会場名
- 演者一覧
- 必要なら購入物件数

ページネーション:

- MVP は 50 件単位
- `page` クエリで切り替え

## 16. バリデーション

- 開催日は妥当な日付であること
- 演者名、会場名は空文字不可
- 同一エントリー内で同じ演者を重複登録しない
- URL は形式を検証する
- 文字数上限を設ける
  - イベント名 200
  - 演者名 200
  - 会場名 200
  - メモ 10000

## 17. バックアップ方針

- SQLite ファイルを定期バックアップする
- 画像アップロードを MVP で扱わないことで運用を簡素化する
- 必要ならエクスポート機能を将来追加
  - JSON エクスポート
  - CSV エクスポート
